# Codex Desktop repository coordination

Use when the user explicitly selects Codex Desktop repository threads for cross-repository work, or when a new turn continues a run that already selected this route. Apply the [native thread contract](threads.md) and [Codex adapter](thread-harnesses.md#codex). The original coordinator owns routing, read-only investigation, independent review and acceptance. The bound keeper owns implementation and repair in its assigned repository worktree.

## Enter or resume

1. Open the workspace-owned matrix and the task's run record or checkpoint. For a new run, use the project's existing record location and record the matrix location and revision, the task and the original coordinator's native address. Keep the checkpoint location in the coordinator's handoff. On each follow-up, after compaction or when reopening the chat, reload those records before deciding who acts. If the matrix changed, reconcile the affected route against the recorded binding. A missing or conflicting record on resume leaves the affected assignment blocked until reconciled.
2. For a new binding, discover the matrix's expected exact title with `list_threads` on the relevant Codex host and read the candidate with `read_thread`. For a resumed binding, read the stored `hostId` and `threadId` directly and check that it still owns the assignment. Verify the actual cwd, Git root, repository identity, Git common directory, worktree, branch and base from observable Git state or the keeper's recorded Git evidence. Resolve application scope from the matrix and repository rules. A title or sidebar match alone leaves identity unverified. The keeper verifies the same facts in its actual working directory before editing.
3. In the existing checkpoint, use the [assignment record](threads.md#discover-and-bind) to bind write ownership to the exact keeper address and worktree, with the human authorization source, permitted actions and readback route. Include the repo/worktree evidence and current attempt, candidate, and last observed cursor as they become available. Use the same record to recover pending sends and review. Keep private addresses and workspace evidence in the owning workspace.

## Route initial work and repairs

1. For a new assignment, send a bounded implementation brief. For an MR review comment, CI failure or additional fix, resolve the affected repository and current assignment from the checkpoint and inspect the failing candidate and source evidence. Record a linked repair attempt under that assignment before sending. Send the affected commit, finding or job evidence, the requested change, allowed side effects and verification to the same bound keeper. Route findings outside the assignment or its authorization through the existing scope decision before dispatch.
2. Use `send_message_to_thread` with the exact recorded `hostId` and `threadId` when direct human authorization covers the target and action. Record submission, then use `wait_threads` with that address and the last cursor, and `read_thread` for the actual return. A peer can leave results in its own chat or a linked project artifact for coordinator readback. On uncertain submission, reconcile the destination turn and checkpoint before considering a retry.
3. Require the return to identify the assignment and attempt, exact candidate commit and base, commands or CI jobs actually run, outcomes and evidence locations, and any gaps. Match the returned commit to the candidate and its checks, inspect the diff and evidence independently, and record the verdict. Keep earlier failures and superseded evidence in the checkpoint. A submitted message, completed turn or check on an earlier commit leaves the current candidate pending.

For missing authorization, an unbound or mismatched thread, an unreachable target, or unclear active write ownership, record the blocker, checked evidence and resume condition. Continue independent work where possible. Keep investigation read-only in the affected repository. Implementation, repair, commits and pushes there remain with the authorized keeper. Run acceptance checks that write files or build outputs in an independently authorized review location.

Use the [first-use evidence](threads.md#first-use-evidence) for each selected client and host before treating the route as operational.

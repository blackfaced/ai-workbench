# 错误与可观测性契约

用于受影响链路的设计、实现和 correctness review。每次先判断适用性：新增或修改输入校验、异常映射、外部调用、异步状态、重试/回调、计量副作用或观测代码时，读取本附件；纯文案、排版等未触及运行行为的变更可写 N/A 及理由。现有证据充分时引用复用，只补本次变更造成的缺口，不要求引入新平台或清理所有历史问题。

## 1. 设计：先明确要回答的问题

沿真实入口和调用方核对现有错误定义、异常映射、日志/指标封装及查询方式。把下列适用项写入项目已有 spec / ticket；小改动可用几句话表达，不另建台账。

| 合同 | 必须说清楚的内容 |
| --- | --- |
| 失败语义 | 哪个条件、哪个阶段失败；已有具名错误码、协议状态、业务/任务状态和安全提示如何对应；调用方能否重试、纠正输入或联系支持 |
| 定位问题 | 用什么关联 ID 查到请求、任务、依赖调用和失败阶段；错误来自哪里；已有日志或 trace 能回答什么、缺什么 |
| 发现问题 | 本次服务行为需要观察的成功/失败、延迟、积压/饱和度或用量；各指标的事件口径、单位、分母和观察窗口；不适用项的理由 |
| 实现与消费 | 在哪个真实生命周期节点记录，由哪个现有组件承担；信号由谁采集、在哪里查询；需要看板/告警时给查询、阈值依据、处理责任人与排查入口 |
| 验证 | 如何触发失败/重试并证明错误映射、信号内容、计数和业务副作用正确；哪些可本地证明，哪些必须真实采集或告警验证 |

保留既有公共错误码、响应字段、指标/标签和查询的兼容性；纠正错误分类或改变统计口径时，明确调用方影响和已批准的迁移范围，不能静默改码、重命名或换分母。项目已有模板、SDK、日志门面和监控设施优先复用。

## 2. 实现：错误码表达真实原因

- 按已确认的失败条件映射具名错误码，先处理明确的领域/校验异常，再用通用兜底处理真正未知的失败。参数约束、资源不存在、权限、超限、依赖超时和内部故障等按项目合同区分；未知错误不能猜成某个已知业务原因。仅历史兼容边界可按已核验的旧码/封装及文案白名单恢复语义，须有误匹配反例与适用范围，不能把任意异常文案当分类依据。
- 在拥有语义的边界统一转换，保留原始异常类型和 cause 链供受控诊断。用户提示包含安全的失败条件及可行动建议；内部路径、堆栈、凭据和原始下游响应不进入公共错误正文。
- 分别表达请求接收、任务执行和结果投递的状态。异步请求已接受不等于任务成功；任务失败、状态写入失败、回调投递失败不能互相覆盖。fallback/retry 保留首次原因、最终结果及尝试关系，重试能力来自合同而非任意失败自动重试。
- 测试断言具体 code、协议/任务状态、提示中的必要信息和副作用。只断言抛异常、非 2xx 或“有错误”不能识别错分类；仅需语义稳定时避免锁死整句文案。
- 有界面消费时，将错误码映射到实际可用的本地化提示与恢复动作；按任务/条目/尝试身份关联适用的失败历史，旧失败不能覆盖新尝试。测试未知错误的中性提示、缺失翻译及部分失败，不把原始下游诊断直接作为用户文案。

## 3. 实现：日志、指标与追踪各自可用

按上面的诊断问题选择最少足够的信号，不要求每个函数都产生日志、指标和 span。

| 信号 | 实现判据 |
| --- | --- |
| 日志 | 在关键状态变化与失败边界记录稳定 event/阶段、结果、error code 和 request/task/trace 等适用关联 ID；按需加入版本与依赖标识。跨线程、队列、回调传递关联上下文。已知业务拒绝与内部故障使用相称级别；在负责处理的边界保留可安全输出的原因，避免每层重复报同一故障。原始异常栈/cause 可能含拒绝值或凭据，不能无条件打印；有泄露风险时使用安全的类别、阶段与关联线索，内部异常链仍保留。 |
| 指标 | 明确统计逻辑请求、尝试、状态迁移还是投递事件；局部条目失败与整体终态分开，计数时机与幂等结果一致，重试/重复回调如何计数必须明确。是否可重试与本次是否最终失败分别记录，不能互推。耗时定义起止事件、单位和时钟；分位数必须有支持它的分布采集/查询。标签采用有界分类，新增 request/task/user ID、原始 URL 或异常文案不作为指标标签。 |
| Trace | 复用已有链路上下文，按实际关键阶段/依赖调用设 span；异步链路按框架支持传播父关系或 link，记录失败与重试关系。明确采样边界，不能因未采到 trace 推断请求不存在。没有 trace 设施时，可用已验证的日志关联满足当前需求，记录限制。 |

日志、错误详情和 span 属性使用字段白名单/脱敏及长度限制，异常 cause 也受同样约束；不记录密钥、临时凭据或无界请求/响应。观测缺失与业务零值分开表达，缺失用量不补成零；诊断指标、用户用量和计费各守已确认口径，不能为方便观测改变账务语义。

## 4. 观测链路自身的失败方式

诊断性日志、指标或 trace 导出失败，按既有 best-effort 合同隔离，不能改变已提交的业务结果或跳过后续必要副作用。审计、账务等必达记录遵守自身持久化/失败合同，不能套用这个原则静默丢弃。

核对适用的超时、缓冲上限、采样/丢弃、重试、去重与延迟可见性。已有 exporter/sink 的失败信号与排查入口优先复用，避免递归记录自身失败。没有可靠投递能力时明确可能丢失的边界；不因发现缺口擅自增加队列、持久化或平台改造，超出票范围的需要另行决策。

## 5. 验证与交付：结论不超过观察边界

沿真实入口选择受影响的正常、具名失败、未知异常，以及适用的重试/重复/乱序回调和观测出口故障场景。分别断言错误分类、关联字段、计数/耗时、脱敏与业务副作用；既有设施可用时验证能够按关联 ID 查到目标阶段，而非只验证 logger/mock 被调用。

| 证据层级 | 能证明什么 |
| --- | --- |
| 设计与源码检查 | 契约、调用位置和消费路径已核对；尚不证明运行时产出 |
| 本地/组件测试 | 指定输入下实际响应、日志/metric/span 内容及故障隔离；Mock 不证明采集部署正常 |
| 真实链路查询 | 指定候选、环境、时间窗和关联 ID 的信号已被采集且可查询；生产端 emit/日志写入成功不能替代这层 |
| 看板/告警验证 | 实际查询口径及适用的触发/恢复/通知路由；数据可查询不能单独证明告警有效 |

评审按通用双层诊断契约记录适用性、依据和未验证边界，作为 correctness 的一部分，不新增评审角色。错误码、语义和期望来自已确认合同及真实消费方，不以实现和测试共用同一映射自证正确。所需证据缺失时，不得将对应验收项写成通过；本地规则/测试通过也不代表规则已分发或线上可观测性已生效。

# 妥协台账

`@RULES_DIR@/rules.md` §2「妥协标记 `lazy:`」的收敛流程。目的只有一个：**别让「以后再说」变成「永远不说」。**

## 扫描

```bash
git grep -n "lazy:" -- . ':!*.md'
```

只扫本仓。跨仓聚合使用目标项目约定的 Issue tracker，不扫描未授权的仓库。

## 分类

每条标记归入一档，档位决定要不要建 Issue：

| 档 | 判据 | 处理 |
| --- | --- | --- |
| **已失效** | 当初的约束没了（量级变了、依赖升级了、上游修了） | 直接改掉，或删掉标记 |
| **需跟进** | 现在够用，但有明确的触发条件会让它不够用 | 建 Issue，标记补 `-> #NN` |
| **长期可接受** | 权衡结论稳定，没有可预见的触发条件 | 留注释，不建 Issue |

**不要给每条标记都建 Issue。** 那只是把代码里的噪音搬到 tracker 里，还多一份要维护的状态。第三档才是常态。

## 建 Issue

Issue 落点按目标项目或分发方的工作环境约定判定。正文四行：

```
**Source:** <文件:行>
**妥协：** <当时选了哪一阶，为什么>
**触发条件：** <什么情况下这个妥协不再成立>   ← 没有触发条件就不该建这个 Issue
**代价：** <到时候改的成本量级>
```

写完把 Issue 号回填到代码注释：`// lazy: ... -> #NN`。

## 输出

一份台账，三档分开列，每档给出条数。重点看两个数：**已失效**的条数（说明标记该清了）和**需跟进**里没有 Issue 号的条数（说明有漏网的）。

# 必要性 Review

`@RULES_DIR@/rules.md` §7 的配套流程。**只回答一个问题：这段代码有必要存在吗。**

## 硬约束

- **不查正确性。** 逻辑对不对、边界处理全不全、有没有并发问题 —— 全部不在本次评审范围内，交给 correctness review。
- 两种评审问的问题不同，混在一起做会退化成一次普通 code review，必要性那一半永远被正确性挤掉。
- 顺序：correctness review 之后、集成测试之前。此时代码已经「对」了，才轮得到问它「该不该在」。
- **不改代码，只出清单。** 删不删由人决定。

## 输入

以下任意一种，都不需要先有 MR：

- 本地未提交变更（`git diff`）
- commit range（`git diff <base>..<head>`）
- 一个 patch / diff 文件

## 检查项

逐个 hunk 过一遍，只找这五类：

| 类别 | 判据 |
| --- | --- |
| 重新发明标准库 | 手写了标准库 / 框架原生能力已覆盖的东西（阶梯第 3、4 阶） |
| 无谓依赖 | 为一两个函数引入新依赖，或已装依赖已能解决（第 5 阶） |
| 投机抽象 | 只有一个实现的 interface、单一产物的 factory、为「以后可能要」搭的脚手架 |
| 无人使用的灵活性 | 没有调用方的配置项 / 扩展点 / 参数开关；不可能触发的分支与错误处理 |
| 越界改动 | 与本 ticket 无关的重命名、格式化、import 重排、邻近「顺手改进」 |

## 豁免（命中即跳过，不进清单）

直接引用 L1 §5 豁免清单：expand–contract 的 expand 阶段、spec 中显式声明的 seam、信任边界上的输入校验、防数据丢失的错误处理、安全、可访问性、用户显式要求的任何东西。

## 输出格式

一份**删除清单**，每项四个字段，按删除收益从大到小排：

```
[文件:行] <一句话说明这是什么>
  命中：<五类中的哪一类 / 阶梯第几阶>
  建议：删除 | 替换为 <更低阶的做法>
  代价：删掉会坏什么（说不出代价 = 可以直接删）
```

清单为空时就直接说「无过度设计」，不要为了凑数把风格偏好写进去。

## 反模式

- 把「我会这么写」当成删除理由。风格差异不是过度设计。
- 提出删除但说不出代价 —— 那说明没看懂这段代码在干什么，先去看调用方。
- 顺手把正确性问题写进清单，稀释信噪比。

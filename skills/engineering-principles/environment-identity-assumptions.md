# 环境与身份能力假设检查

`@RULES_DIR@/rules.md` §4 开工门禁与 §7 身份合同核验的配套方法。**只回答一个问题：这段设计/改动到底假设自己跑在什么环境、用什么身份、消费什么能力。**

开工门禁管「代码合同与调用链」，本文件管「代码合同之外、写在假设里却从没写下来的那一层」。假设不写下来，评审现场就只能靠运气发现；环境或身份一变，线上才知道哪里碎了。

## 何时用

- 写技术方案 / RFC / ADR 的现状核对与设计阶段：当作必答维度表。
- 跨系统改动派发实现之前：当作最小授权契约探针（contract probe）的输入清单。
- 代码评审判断身份合同是否适用时：用下面的适用性判据决定要不要走 §7 核验。
- 复用现成技能 / 工具 / MCP server 时：在接入前确认它假设的环境与身份和目标部署一致。

不适用的项目也要明确标「不适用」并写理由，不能因为是内部小工具就跳过——内部工具最容易假设「跑在我这台机器上、用我的账号」。

## 九个必答维度

每维产出一行：`假设内容 | 依据（工具定位到的事实） | 未验证边界`。依据必须由工具实际定位过（`glob_search` / `grep_search` / `read` / `git log` / codebase 查询 / 只读探测），不允许凭记忆写符号名或环境值。定位不到的降级成「待核对」，不伪装成事实。

### 1. 外部依赖

- 依赖哪些外部服务 / 中间件 / 第三方 API / 内部平台？版本或契约版本是什么？
- 调用是同步还是异步？超时、重试、熔断策略？依赖不可用时本服务的降级路径？
- **判据**：把每个外部依赖写成一行，标注「硬依赖（挂了就不能跑）」还是「软依赖（可降级）」。

### 2. 所需能力

- 依赖目标运行环境提供什么能力？例如：操作系统版本、shell 可用性、运行时版本、权限模型、网络出口策略、文件系统路径约定。
- 这些能力是代码里直接调用的（`os.system` / 特定 syscall / 特定环境变量），还是通过配置隐式假设的？
- **判据**：每写一个对环境的调用，就在表里记一行它假设了什么；环境一变这行就会碎。

### 3. 环境差异

- 开发 / 测试 / 预发 / 生产之间有什么差异？配置、拓扑、数据量、权限范围、网络可达性。
- 哪些差异是代码必须感知的（`if env == prod`）？哪些应该由配置注入而不是写死？
- **判据**：列一张「环境差异表」，对每行判断它是被显式配置驱动，还是被代码里的分支硬编码。硬编码的差异是评审重点。

### 4. 身份 / 区域绑定

- 这段代码以什么身份运行？进程身份（daemon / 用户 / service account）、API 调用身份（token / AK-SK / OIDC）、数据归属身份（哪个租户 / 哪个用户 / 哪个项目）。
- 身份是从哪里来的？环境变量？配置文件？挂载的密钥？平台注入的 metadata？
- 身份绑定在哪个区域 / 集群 / 实例上？换区域还能用吗？
- **判据**：画出「凭据来源 → 实际生效主体 → 资源 Owner → 权限/持久化结果」这条链。链上任何一环换了，行为就可能变。这条链就是 §7 身份合同核验要追的东西。

### 5. 配置来源

- 所有可调参数从哪里读？环境变量、配置中心、本地文件、命令行参数、代码里的默认值。
- 每个配置项的默认值是什么？默认值在生产环境是否安全？
- 配置缺失时代码的行为？是 fail-fast 还是静默用默认值继续跑？
- **判据**：把所有配置项列一张表，列名 = `配置项 | 来源 | 默认值 | 缺失行为 | 是否安全默认`。

### 6. 规模 / 拓扑假设

- 假设数据量多大？QPS 多少？并发多少？存储上限？
- 部署拓扑是单实例还是多副本？有无主从？有无跨机房？
- 这些假设写在代码里（硬编码的 buffer size / 线程池大小 / 分片数）还是写在配置里？
- **判据**：找硬编码的魔数，每个都问「规模翻 10 倍会怎样」。答不上来的就是未验证边界。

### 7. 失效方式

- 每类外部依赖失败时，代码怎么表现？报错？静默降级？数据写一半？重试直到成功？
- 进程被 kill / 机器重启 / 网络分区时，状态能恢复吗？恢复点在哪？
- 权限过期 / token 轮转失败 / 配额打满时，行为是什么？
- **判据**：对每个外部依赖写一条「失败路径」，标明这条路径是测过的、设计过的、还是没考虑过的。没考虑过的就是缺陷候选。

### 8. 兼容 / 不支持选择

- 明确不支持什么？不支持的环境版本？不支持的身份类型？不支持的区域？
- 不支持时是显式报错（fail-fast，带清晰错误信息）还是静默跑在不支持的配置上？
- 对老版本 / 旧调用方的兼容策略？是 Adapter、Optional 字段、默认关闭开关，还是直接破坏？
- **判据**：列一张「明确不支持」清单，每行标「显式报错」还是「静默降级」。静默降级到不支持的配置是评审红线。

### 9. 验证证据

- 以上每条假设，用什么证据证明它成立？只读探测结果？测试？文档引用？已验证的运行态？
- 证据是独立于当前 spec 和 Mock 的真实消费方实现 / 运行态，还是只靠字段名和同源断言？
- 哪些假设还没有证据？没有证据的是「待核对」而不是「已确认」。
- **判据**：每个假设行末尾必须有一个证据指针（命令输出 / 文件路径 / 测试名 / 文档链接）。没有指针的假设等于没验证。

## 身份合同适用性判断规则（代码评审时）

§7 要求每次代码评审判断身份 / 权限 / 资源归属是否受影响。下面的判据用来决定**是否适用**，避免评审者凭感觉选「不适用」。

### 触发「适用」的信号（命中任一即适用）

- 变更直接读写凭据、token、密钥、身份相关环境变量或配置项。
- 变更修改权限判断、资源 Owner 解析、租户 / 用户 / 项目隔离逻辑。
- 变更改变外部 API 调用的身份、作用域、区域绑定，或改变被调用方解析身份的方式。
- 变更引入新的外部依赖，且该依赖有独立的身份 / 权限 / 配额模型。
- 变更修改持久化数据的归属（把数据从一个租户 / 用户换到另一个）。
- 变更改动 daemon / service 的运行身份、启动用户、或挂载的密钥。
- 评审者从 diff 看不出调用链——这时默认按「适用」处理，先追清楚再决定。

### 可判「不适用」的条件（全部满足才可判不适用）

- 变更完全不触碰：凭据、权限判断、资源归属、外部调用身份、持久化数据归属、运行身份。
- 变更的调用链在同一进程内闭环，不跨信任边界、不跨身份域、不跨区域。
- 评审者能在 diff 里直接看到所有读写路径，没有未追的外部调用方。
- 三条同时满足时，在评审记录里写一句「不适用：变更范围局限于 <具体模块>，不涉及身份/权限/资源归属」。

### 适用时必须产出的结论

不是「看了一眼没问题」就过。结论必须是三选一，并写在评审记录里：

1. **已核验**：从凭据来源追到权威消费方、实际主体、资源 Owner、权限/持久化结果；证据是独立于当前 spec 和 Mock 的消费方实现或已验证运行态。
2. **发现缺陷**：身份链路上某处行为与假设不符，报缺陷。
3. **证据不足，不得宣布通过**：缺独立证据时，零 finding 也不能替代核验完成；必须显式标注「缺证据」并说明需要补什么。

## 工具与方法

- **定位符号与调用链**：`grep_search` 找调用方，`glob_search` 找文件，`read` 读实现，`git log` 追变更历史。不允许凭记忆写类名 / 方法名 / 配置项名。
- **只读环境探测**：在目标环境跑只读命令确认假设（例如查环境变量是否存在、查配置中心值、查 API 是否可达）。写操作 / 计费调用需要已确认的执行授权，不能私自跑。
- **契约探针**：跨系统改动派发实现前，用最小只读请求确认对方的公开标识符、认证角色、入口点、响应形状；包括分页，不能因为没看到结果就推断对方没有。
- **证据归档**：探测输出、命令、版本号连同假设表一起存档，作为 §9 验证证据行的指针。散落在聊天记录里的探测结果不算证据。

## 输出格式

一张表，每行一个假设：

```
| 维度 | 假设内容 | 依据（工具/探测事实） | 未验证边界 |
| --- | --- | --- | --- |
| 外部依赖 | ... | ... | ... |
| 身份绑定 | ... | ... | ... |
| ... | ... | ... | ... |
```

表后面接一段「评审适用性结论」：本次变更是否触发身份合同核验、三选一结论、缺什么证据。

## 反模式

- 把「跑在我这台机器上能用」当成环境假设已验证。个人开发机不是生产环境。
- 把配置默认值写成「生产安全」却没有读过配置中心的实际值。默认值是设计意图，不是运行事实。
- 把「不支持 Windows」当成兼容选择，却没有在不支持时 fail-fast——代码会在 Windows 上静默跑出错误行为。
- 评审时看到 diff 不涉及登录代码就直接判「身份不适用」，却没追这个服务被谁调用、调用方用什么身份。
- 证据只来自单元测试的 Mock——Mock 证明你写的代码按你想的方式调用了自己，不证明真实消费方接受这种调用。

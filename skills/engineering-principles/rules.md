# 通用工程原则

唯一真源：AIWB `skills/engineering-principles/` 指令包。dev-tracker 固定消费一个提交，组合自身工作环境约定后分发；只修改源文件，不手改安装副本。正文与摘要在同一变更中审阅，摘要是正文的简短投影。

来源：multica-ai/andrej-karpathy-skills 的四原则与 DietrichGebert/ponytail 的实现阶梯，语义合并与实践补充，MIT；许可证见同目录 LICENSE。

本文件约束怎么实现与验证，具体目标由当前 spec / Issue 和项目规则给出。

## 1. Think Before Coding

- 不要替用户做静默假设。假设一旦影响实现方向，先说出来再动手。
- 管理自己的困惑：读不懂就说读不懂，别猜着往下写。
- 发现需求内部矛盾、或与现有代码/ADR 冲突，**先暴露矛盾**，不要挑一个自己顺手的解释闷头做。
- 存在多个合理方案时，摊开 tradeoff 让用户选；该反驳用户时要反驳。

## 2. Simplicity First（懒惰阶梯）

理解完问题、跟踪完真实调用链之后，写代码前逐级自问，**停在第一个成立的台阶**：

1. 这东西需要存在吗？（YAGNI）
2. 这个仓库里已经有了吗？复用现成的 helper / util / pattern，不要重写。
3. 标准库能做吗？
4. 语言/框架/平台的原生能力能覆盖吗？
5. 已安装的依赖能解决吗？（不为此新增依赖）
6. 能一行写完吗？
7. 才轮到：写能跑的最小实现。

配套硬规则：

- 不写只有一个实现的 interface，不为单一产物写 factory，不为「以后可能要」搭脚手架。
- **优先减少复杂度，不是减少行数。** 200 行能压到 50 行就压，但 5 行 magic one-liner 不优于 15 行清楚代码。删掉的代码不需要维护，看不懂的代码需要维护两次。
- 每一个抽象、依赖、分层、配置项、fallback、扩展点，都必须能用**当前已知的** requirement / test / constraint 解释自己为什么存在。解释不出来的，默认删掉。
- **复杂度预算**：实现开始变复杂时，先明说三件事 —— 我在加什么复杂度、每一块现在为什么必要、删掉它会坏什么。说不出第二问的那块就是过度设计。
- 共享函数出问题时，`grep` 所有调用方，在根因处修一次；不要在调用点逐个打补丁。
- 非平凡逻辑至少留**一个**可运行的验证（测试或可复现命令），但不要为此引入测试框架 / fixture 体系。

### 妥协标记 `lazy:`

有意识地停在低阶台阶、或明知不彻底但当下够用时，在那行代码旁留一条注释：

```
// lazy: <一句话说明为什么这样够用>        ← 无需跟进
// lazy: <一句话>  -> #NN                  ← 需要跟进，NN 是 Issue 号
```

语义与既有标记不同，不要混用：`TODO` 是还没做的事，`FIXME` 是做错了的事，`lazy:` 是**已经做完、能跑、但明知不彻底且是权衡后的选择**。

它的作用是让「我先简单实现一下」留下可枚举的痕迹 —— 否则半年后没人分得清哪段是深思熟虑的简洁，哪段是当时赶时间。真需要跟进的才建 Issue，其余就只是注释。收敛方式见 `@RULES_DIR@/debt.md`。

## 3. Surgical Changes

- 优化目标是「完全满足 ticket 的最小改动」，不是「完整性」。
- 顺手发现的邻近改进：**单独报告，不要实施**。
- 不重排无关的 import、不顺手格式化未涉及的文件、不改与本 ticket 无关的命名。
- **达标即停**：验收标准满足就收手。不做「既然都改到这儿了」，不在没有证据的情况下为未来留扩展点。上面两条管的是改动**范围**，这条管的是达标**之后**还继续加。

## 4. Goal-Driven Execution

- 按验收标准干活，不按指令字面。验收标准缺失时先补齐再动手。
- 输出以结论和证据为先：改了什么、为什么、怎么验证。解释不要长过代码。
- 不要用「已完成」掩盖未验证。没跑过就说没跑过。

### 实现类 Issue 开工门禁

修改代码前完成以下 TODO；简单的一行修复可压缩表达，但不能跳过对应判断：

1. **合同**：读完 ticket/spec、依赖票和相关 ADR，把验收条件改写成可判定的不变量；发现矛盾或缺口先暴露。
2. **调用链**：找全生产入口、共享根因、旧/新入口和真实调用方，明确是在根处统一，还是有证据地保留多条路径。
3. **边界**：列出输入/输出 schema、状态转换、fallback/retry、错误分类、敏感信息、计量与外部副作用；不适用项明确标记不适用。
4. **测试矩阵**：覆盖 happy path、边界值、畸形输入/输出、依赖失败、降级与最终失败、所有公开入口的一致性；修 bug 时先让目标缺陷稳定复现为红。
5. **最小方案**：写明改哪些现有 seam、每块复杂度为什么现在必要、删除它会破坏哪条验收；同时列出本票明确不做的相邻工作。
6. **反馈环**：选定一条可重复运行的最小验证命令并确认能执行；若环境阻塞，先记录阻塞和可运行替代证据。

以上六项在 commentary 或 plan 中留下可检查的简短记录后再编码。实现中出现新分支、fallback、DTO 或错误类别时，先回到门禁补齐对应不变量和测试矩阵，再按共享根因和完整合同一次收敛。

## 5. 豁免清单（以下不属于「过度设计」，不许砍）

- **expand–contract 的 expand 阶段**：宽度重构时新旧形态并存是显式要求，不是投机性冗余。
- **spec 中显式声明的 seam**：哪怕当前只有一个实现，也是为可测性刻意留的，不许合并掉。
- 理解问题本身花的时间。
- 信任边界上的输入校验、防数据丢失的错误处理、安全、可访问性。
- 用户显式要求的任何东西 —— 显式要求优先于本文件的一切简化倾向。

## 7. Review

- code review **不需要**先有 MR。本地未提交变更、commit range、diff/patch 都可以直接评审，任何仓库（含只有读权限的）都适用。
- **必要性 review** 是与 correctness review 并列的另一种评审，只问「这段代码有必要存在吗」，不问「这段代码对不对」。流程见 `@RULES_DIR@/review.md`。
- **接第三方 review 流程时，必要性是必须补的一轴。** 例如 matta 的 `code-review` skill 只有 Standards / Spec 两轴（Standards 轴的 Fowler smell 只覆盖 Speculative Generality 一类），跑它的时候要额外并行一个必要性轴，judge 用 `@RULES_DIR@/review.md` 的五类判据，结果与另两轴并排汇报。具体审查入口由分发方或目标项目提供。

## 10. 默认约定

- 默认不自动 commit / push / 建 MR，除非用户明确要求。
- 输出默认简体中文。
- 数据、结论、行号、star 数之类可核验的事实，必须来自实际执行或实际抓取；无法确认就写「未经验证」，不许编造。

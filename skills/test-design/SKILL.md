# Test Design

Domain: coding

从需求、旧合同和实际调用关系推导能识别错误的测试设计，并审查设计是否可执行。适用于单需求、改动前设计及现有用例审查；可独立使用，不要求启动交付流程或测试平台。正文以 AI Workbench 为真源，业务用例、物料和证据留在所属项目。

本 Skill 只负责**设计与质量审查**。读取资料并更新已授权的项目设计载体，不启动开发、部署、测试执行或额外 agent，不因设计需要扩大外部操作权限。设计审查结论不等于执行 PASS。沿用项目的期望值负责人和验收权限；只给出设计建议，不能自行接受交付。

## 阶段一：设计

### 1. 固定依据与载体

读取当前需求及已确认调整、候选/基线、真实入口与调用方、现有测试/验收文档、适用的项目经验及样本。记录版本或可追溯位置；未提交改动用 base SHA 加 patch 摘要识别。不要从实现倒推业务应当如此，也不要把失效的历史经验变成全局要求。

先找既有验收载体，保留稳定用例 ID、旧预期、失败与复跑记录。已有覆盖以引用复用，只补有证据的缺口；无相关变更且设计仍有效时，说明复核依据，不机械新增用例。确无合适载体时，按项目约定使用 [最小设计结构](assets/design-template.md)，不要另建用例数据库或结果台账。

需求矛盾时列出冲突来源与影响，不默选一种解释。缺业务判据、物料或关键合同，记录已查来源、未知事实和解除条件；继续设计不依赖它的部分，不编造期望或数据可用性。

### 2. 从不变量选择场景

先写“无论如何变化，什么必须成立”，再为每条候选用例说明一个**错误但看似合理的结果**。沿实际入口追到承担该行为的边界及共享调用方，选择能够触发并观察这个错误的最短动作序列。已有测试足够时引用它，不为增加数量重复实现。

按相关性选择正常路径、边界值、畸形输入、依赖失败/恢复和副作用；每个场景写风险依据。以下维度只在合同涉及它时展开，不生成全组合：

- **状态与顺序**：考虑 A → B → A 后下一次操作、取消后迟到响应；在要求的中间态和最终态分别观察，不能用最终截图证明先后顺序。
- **重试与输入**：确认重试使用冻结输入还是当前值，控制失败与释放时机，在真实调用方观察请求及结果；固定 sleep 或 helper 相等不能证明调用链。
- **兼容性**：列出旧可观察合同、实际调用方、配置默认值/权限/持久化数据/错误/时序与副作用的适用边界。设计旧入口的前后回归；新路径通过、构建成功不能替代旧路径证据。保留旧断言，具名破坏性迁移需已有明确批准。
- **身份、权限与归属**：每次判断适用性并说明依据。适用时从凭据来源追到权威消费方、实际主体、资源 Owner 和持久化/权限结果；期望值须来自独立于当前 spec 及其 Mock 的消费方实现或已验证运行态。字段名、同源断言或自造 Owner 不构成证明。缺权威判据时保留未决，不宣布审查通过。

### 3. 把用例落到可执行断言

每条新增或增强用例写清以下最小字段；多个字段可合并表达，不能省掉含义：

| 字段 | 要回答的问题 |
| --- | --- |
| 稳定 ID 与来源 | 对应哪条需求/旧合同、哪个版本？已有覆盖在哪里？ |
| 不变量与待检测错误 | 哪种错误必须被识别？为什么当前改动会触及它？ |
| 适用边界 | 哪个生产入口、调用方与观察边界？哪些维度不适用及原因？ |
| 数据与前置条件 | 环境/角色/物料的必要属性是什么？从哪里取得，是否已确认可用？ |
| 动作 | 如何可重复地触发目标分支/顺序？引用现有命令或清晰动作，勿编造 API。 |
| 业务断言 | 在何处观察什么值/关系/副作用？判据的独立来源是什么？ |
| 证据层级 | 源码检查、生产函数测试、模拟依赖的入口测试或真实联调；执行/绕过哪些层？ |
| 未决缺口 | 缺什么、查过什么、影响哪些断言、恢复条件是什么？ |

先复用现有测试、已验证样本和历史有效运行输入。说明样本为何能触发目标边界，区分“可读取”“属性满足”和“运行已验证”；负样本可按合同构造，正样本优先从已验证输入派生。物料不可获得时不填写虚构可执行步骤。

断言要观察业务结果及适用副作用，避免只检查 HTTP 成功、非空、没有报错或截图存在。异步行为用可观察完成事件/受控挂起释放，必要时检查请求次数、资源归属、写入后重新读取及清理效果。使用项目已有执行器，不为本次设计创建新测试框架。涉及真实付费、共享数据或敏感信息时标明既有权限和脱敏/清理要求；设计本身不授权执行。

## 阶段二：质量审查

逐项审查新增/变化用例及受影响的既有覆盖。复用仍有效的审查证据，不盲目重建全表：

1. **断言会不会放过目标错误？** 把阶段一的错误结果代入断言：若仍通过，指出漏检机制并改到承担行为的观察边界。记录该推演是设计审查，不能冒充已运行缺陷版本。
2. **期望是否独立？** 检查是否把实现逻辑重算一遍、Mock 同时产生输出和期望、用同一字段互相验证。替换为需求合同、已核验权威消费方或独立已知样本；没有可靠判据就记未决。
3. **能否触发且不会误报？** 数据是否真的满足前置？错误是否在目标逻辑前就被无关校验拒绝？设计错误条件应失败、正确条件应通过的对照，区分受控错误与真实服务。尚未执行的对照只叫验证计划。
4. **覆盖是否有缺口或重复？** 逐条对照需求与调用关系，解释遗漏、无关和已有覆盖。合并重复场景时保留 ID/来源映射和历史结果，不用“更多用例”代替有效性。
5. **证据范围是否被夸大？** 仅有 Mock 时写明真实依赖、权限、服务行为或质量仍未验证；单一客户端/环境的证据不得外推。身份适用项无独立权威依据时，审查保持未决。

输出简短设计审查结论：已就绪的用例、改进点及未决边界。清楚区分**设计已就绪**、**尚需判据/前置条件**与项目自己的执行状态；不额外创建一套执行状态枚举。没有实际执行不能产生 PASS，设计完成也不能把原 NOT_RUN/BLOCKED 或历史 FAIL 改为通过。

在原验收载体更新预期时保留旧版本和变更理由，指出哪些旧证据需重新核验。执行结果继续写入项目原有唯一记录，报告只汇总/引用；本 Skill 不复制维护第二份结果表。交付引用设计位置、需求/候选版本、复用范围与未验证边界，达标即停。

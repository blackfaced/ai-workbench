# Botmux project-context startup

Use after the owner authorizes automatic setup for specified projects. This opt-in integration prepares the selected checkout before the native CLI starts, including worktrees created through Botmux's own picker or another Git entry. Botmux continues to own sessions, roles, input, model selection and transport.

## Verified runtime and installation

Botmux 3.40.0 local tmux + bash passes `-i -c SCRIPT _ CWD ENV... CLI ARGS...` through `launchShell`. Install a small executable named `bash` in an owner-managed stable release directory. It calls the pinned release's `botmux_context.py --registry <owner-registry> --shell /bin/bash -- "$@"`. The gate prepares CWD synchronously, then execs the original bash with every argument unchanged. Bind it through the existing per-bot `launchShell` setting; preserve the original setting and a guarded rollback record. The release installer includes the gate and its shared I/O helpers in its hash manifest.

Recheck installed-version source and actual argv before enabling. This contract is specific to local bash launches: strict-env/sandbox paths can bypass the shell, and remote, adopted, already-running, RPC-only or other-shell paths are not covered. Do not claim this gate protects them. `session.start` lifecycle notifications run asynchronously after startup; prompt-submit gates do not cover every startup path. Neither substitutes for pre-exec preparation.

Use Botmux's existing authenticated local configuration endpoint to set `launchShell` without switching CLI identity or restarting live workers. Verify both persisted and effective settings and preserve active session IDs/PIDs. Never log the shared IPC secret, request headers, environment assignments, CLI argv or raw native input. A direct bots.json edit alone does not prove the running daemon adopted a setting.

## Project-owned registry

Keep an owner-only version-1 JSON registry outside business source control. It contains:

- `installer`: stable `setup-aiwb-context` path and its SHA-256.
- `clients`: absolute native `codex` and `trae` executable paths. These remain the real clients, avoiding recursive startup checks.
- `projects`: keyed by canonical Git common-dir. Each entry declares canonical `repo`, `declaration` and `declaration_sha256`, rules `pin`, existing `workenv`, absolute `companions` with SHA-256, reviewed relative `source_files` with SHA-256 (null records expected absence), and `team_sha256` for root AGENTS.md.

Optional `native_companions` maps relative `.trae/` or `.codex/` artifact paths to pinned `{source, sha256, worktrees_only?}` entries. `worktrees_only: true` limits provisioning to additional checkouts while retaining the source checkout's own native metadata. These are copied only when absent; matching existing files are retained, conflicts and tracked/unexcluded paths block startup. Native config files themselves remain owned by the renderer. Use this for verified project-local client startup metadata. On TraeX 0.209.1, choosing “Do not ask again for selected data” creates `.trae/.coco-resources-migrated` with `skipped_by_user=true\n`; explicitly provision that project-local skip decision when legacy resources would otherwise prompt. Preserve team `.coco` content and global migration preferences. Verify the installed client behavior before registering this compatibility artifact.

Use the project's existing declaration and analysis record. Include referenced rules/observability documents in companions. Registration authorizes exact checkout trust provisioning when Botmux selects a real root of that registered Git repository; it never trusts a parent or matches repositories by remote URL/name. Keep private native paths in that Git common-dir's existing local excludes before registering. Existing explicit untrusted values, foreign native blocks, symlinks and source drift retain the renderer's refusal behavior.

A worktree may use a different commit only while all reviewed files and team guidance still match. A changed error adapter or observation helper requires the project's setup analysis to be refreshed; an unattended shell gate cannot perform that analysis. Shared source pointers are appropriate only when their registered main-checkout source has a stable lifetime. Missing/moved sources block startup.

## Runtime and verification

The gate serializes starts for one registered repo, validates pinned inputs, runs the renderer's apply and check with the selected explicit worktree, then inspects both native clients' no-model input from that exact cwd. Project instructions, rule pin and complete team guidance must be present in their expected roles. Any failure exits 78 with `AIWB_CONTEXT_STARTUP_BLOCKED`; the shell and business CLI are not executed. A sanitized refusal record is saved at `<registry-directory>/failures/<cwd-sha256>.json`, because a failed tmux pane may disappear before its stderr can be inspected. Unregistered repositories pass through without project/trust writes.

The selected checkout gets `.ai-workbench/project-context/botmux-startup.json`: source/target revisions, registry/declaration hashes, cwd, timestamp and sanitized loading checks. Renderer backups and ownership ledger remain in the registered source checkout. This receipt proves provisioning/loading, not model behavior or live telemetry collection.

Before declaring completion, create a fresh Git worktree without native configs and start it through the ordinary configured Botmux entry. Persist actual Botmux/native session IDs, cwd, startup receipt timestamp preceding native session creation, developer/team input and a pinned readable project-document pointer. Record any model-backed document-read probe separately: capacity queueing does not invalidate persisted startup-input evidence, but must never be reported as a successful model action. Exercise a source/foreign-config failure and prove no native session started. Repeat setup and compare native hashes; check an unrelated Git repository receives no private context. Close only owned probes, remove only clean owned worktrees, and restore only exact probe trust entries/ledger rows under ownership guards. Retain the setup source, backups and sanitized evidence.

Tests: `python3.11 tools/environment/tests/test_botmux_context.py`, the existing project-context suites, and `python3 tools/environment/tests/regression.py`.

Protocol source: [Botmux 3.40.0 tmux backend](https://github.com/deepcoldy/botmux/blob/v3.40.0/src/adapters/backend/tmux-backend.ts), [launch-shell configuration endpoint](https://github.com/deepcoldy/botmux/blob/v3.40.0/src/core/dashboard-ipc-server.ts). ## Direct terminal startup

For an authorized direct CLI entry, install `cli_context.py` from the same pinned tool release. It calls the shared `botmux_context.prepare` function, then execs the registered native client with scoped declared defaults followed by original argv, preserving cwd. Record native absolute paths separately from wrappers to prevent recursion. Keep installer-owned client symlinks intact; use an owner-managed PATH directory and a small backed-up shell initialization block. Verify resolution from fresh interactive/login shells and retain guarded rollback hashes. Native updates keep their existing installation path; check the wrapper resolution again after updates.

When the source AGENTS.md itself is private, untracked and locally excluded, an explicit `private_team_guidance: true` registration permits copying that pinned file only into an absent, untracked/excluded target AGENTS.md. Preserve matching existing guidance and refuse conflicts or tracked targets. Record this private artifact separately from tracked team guidance.

Register only reviewed Git common-dir identities and project-owned sources using the registry above. A new worktree reuses that analysis and rule pack: materialize the owned native instruction blocks, establish exact-checkout trust, and check real native loading. It does not rerun repository analysis, business builds or service setup. Changed reviewed sources require a setup refresh rather than copying stale context.

The direct adapter supports existing checkout roots/subdirectories, `-C DIR`, `-CDIR` and `--cd=DIR`, interactive new sessions, `exec`/`review`, and `debug prompt-input`. It inspects config/profile overrides with the real loader before native exec. Parsing stops at the first prompt or `--`; argument strings are never shell-evaluated or persisted. Unregistered projects, help/version/update and management commands pass through. Existing-session resume/fork and long-lived app-server/ACP/remote paths keep native behavior and are outside new-session setup coverage. Registered starts with unknown options or context-disabling flags refuse. Native `--worktree` starts use the synchronous materialization gate below; Desktop uses its native Local Environment setup script. These require independent installation and verification before claiming coverage.

Each checkout stores `.ai-workbench/project-context/cli-startup.json`; refusals use the same sanitized owner-local failures directory. Verify independently fresh worktrees through both command names, directory overrides, idempotence, foreign config preservation, and unrelated/same-origin-clone isolation. No-model loading evidence establishes initial context, not subsequent model behavior or production telemetry acceptance.

A registered direct-CLI project can set `client_defaults` to `{"codex":{"project_doc_max_bytes":65536},"trae":{"project_doc_max_bytes":65536}}` when actual native input proves its team guidance exceeds the client's default document budget. The adapter permits only this bounded integer setting (32 KiB–1 MiB), applies it in both native loading probes and the final command, and leaves unregistered projects unchanged. Original CLI arguments follow the defaults, so explicit owner overrides remain visible and are verified; an override that truncates required guidance blocks startup. This is a direct-CLI registry setting, not an automatically supported Botmux launch option. Verify and record the required budget from real input rather than setting a machine-wide maximum.

## Native CLI worktree creation

Codex 0.162.0 and TraeX 0.210.1 create native Git worktrees with `worktree add --no-checkout`, then synchronously materialize with `--work-tree=. reset --hard --no-recurse-submodules`. Both set `core.hooksPath=/dev/null`, so ordinary Git hooks cannot prepare their new checkout. Preserve native name/base/branch/allocation behavior. For an explicitly registered repository, arm a one-launch owner-local token and prepend a pinned Git proxy only to that native process tree. After the native Git materialization succeeds, `native_worktree.py` verifies exact common-dir identity, calls the shared prepare function, and returns to the native client only after complete native loading succeeds. It adds no agent loop and installs no global Git hook or global Git wrapper. Later Git calls pass through after the token is completed.

Register `native_worktree` with absolute real `git`, pinned `shim` / `shim_sha256`, and exact tested first-line client `versions`. An upgraded client requires revalidation before this path is enabled. The integration supports native Codex `--worktree` and TraeX `-w` / `--worktree` names and bases in Git mode. TraeX receives a scoped `--worktree-mode git` default; explicit reflink mode is refused until separately verified. Remote, resume/fork, adopted and long-lived server paths remain separate contracts. Preserve every original native argument after scoped defaults. Never persist prompts, full argv, private config overrides or environment values in tokens or receipts.

Pending token state lives beside the registry. A refusal saves the sanitized failure before native creation reports failure; retained-checkout / rollback behavior remains the client's own. Do not delete live tokens or remove a retained checkout without checking its owner and changes. Verify fresh native creation through actual client invocations, first request/context timestamp after PASS, foreign-source/drift failure, names/base selection, stdin, and unrelated-project isolation. A `debug prompt-input` invocation with `--worktree` is unsupported by these versions and is not a creation test.

## Desktop Local Environment setup

Use the app's supported project `.codex/environments/environment.toml` with a synchronous `[setup].script` invoking an owner-managed pinned `native_worktree.py --desktop` launcher. The app supplies `CODEX_SOURCE_TREE_PATH` and `CODEX_WORKTREE_PATH`; the helper verifies their Git relation and registered identity, reuses prepare, then checks the actual bundled Desktop CLI as well. The app awaits setup before starting the new thread and treats nonzero exit as setup failure. Keep the setup environment selected for this project; explicit user selection of No environment bypasses it. Preserve any existing project environment/actions/platform setup, local exclusions and selection. Keep this personal environment private unless its owner explicitly chooses to share it.

Record Desktop's absolute bundled CLI separately as `desktop_client`. For complete guidance that needs a larger document budget, put `clientSettings` in the project declaration (only bounded `project_doc_max_bytes` per client is supported). The renderer manages this scalar inside its existing owned instruction block so Desktop loads it without terminal-only flags. A user-owned sufficient value is retained; a conflicting smaller value is refused. This declaration is the source of truth; retire equivalent direct-CLI `client_defaults` after provisioning and native checks pass.

Verify Desktop-created worktrees independently from CLI-created worktrees. Check actual selected environment, setup receipt before first thread/input, full team/private guidance through the bundled binary, no other-project markers, and refusal behavior. Tool-created files or a manual invocation of the setup command do not establish app UI coverage. If desktop UI tools are unavailable, finish the configuration and CLI checks, report that exact boundary, and request the concrete app creation step for final verification. Never claim a successful Desktop click from source inspection alone.

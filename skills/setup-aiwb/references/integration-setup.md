Prepare or maintain integration-test instructions in the project's existing Issue tracker, using its actual development and deployment entry points. This is a Skill, not the retired `aiwb setup` CLI. Reuse maintained repository guides, scripts and CI as sources; link them from the Issue instead of creating `docs/testing` files. For multiple repositories, each owns its instructions; link their Issues and sources rather than copying deployment procedures.

## Inspect and write the Issue instructions

Read repository rules and the existing test/run/deploy documentation, package scripts, CI, deployment manifests, and relevant callers. Identify the tested system boundary and the source of each command. Inspect existing configuration and credential-provider availability without printing secrets; ask only for missing inputs or unresolved choices. Distinguish configured, reachable/authenticated, and behaviorally verified. Configuration presence is not proof of a working test environment.

Use [the guide outline](integration-guide.md) to record only applicable sections. Capture exact working directories, executable entry points or script links, prerequisite versions, variable names and retrieval methods, service dependencies, readiness checks, target identity, test commands, evidence collection, and cleanup. Mark inferred commands or unexecuted steps UNVERIFIED with the unresolved question. A guide can be complete as a draft without claiming its commands work.

For frontends, prefer the repository's local development command (such as `pnpm dev`); verify the actual script, port, ready signal, API routing, test-account source, and browser/test runner. For backends, prefer an isolated Kubernetes development Pod with incremental file/artifact copying for iteration, using the repository's supported build/chart/values and development procedures. Verify context/namespace, Pod/container identity, base image, copy destination, activation/build/restart command, readiness, access route and logs. If this path is unsupported, surface the concrete gap and agree on an alternative. These are inspection criteria, not universal commands or permission to deploy. Do not assume a separate Pod isolates shared databases, buckets, queues, or APIs.

Writing the requested instructions is authorized setup work; publishing or updating an Issue still follows the project's existing write authority. If invoked as part of `deliver-spec`, reuse its confirmed execution plan. Keep a controlled draft when the tracker or write authority is unavailable and report the pending write; do not substitute a new repository report. Present concrete operations, targets, side effects, costs when relevant, and cleanup before executing actions not covered by existing authorization. Reuse the batch confirmation instead of creating another approval ritual. Read-only discovery may precede it; deployments, real API calls, and test-data writes may not.

## Validate and maintain

After authorization, execute only the necessary setup/health checks within the agreed test boundary. Record the actual command, date, source commit, environment, outcome, and evidence reference for each verified path. Pin the deployed candidate to a commit/image digest or report identity as unverified; testing an old service does not verify the new implementation. Use named test resources and clean up only resources created by this run within authorized scope. Report remaining resources and cleanup failures.

When verification uses a development service, establish one service owner and record its worktree/candidate (including uncommitted patch identity), process/session, URL/port, access method and stop/restart procedure in the Issue instructions or linked attempt comment. Verify an actual HTTP/API response and browser access where needed, not just a Ready log. For human checks, provide a reachable authorized URL, concrete actions and expected behavior, then record the user's actual feedback separately from agent-run tests. Opening public access or changing shared network configuration requires separate authority.

Reuse that entry point across iterations when practical: its owner updates the served candidate through the approved integration path, reloads/restarts as needed, verifies candidate identity and readiness, and records affected check results. Worker worktrees remain isolated; other workers do not overwrite the served worktree. A stable URL is not a stable version. If the owner or endpoint changes, update the handoff before further checks. Retain the service only for the agreed review window, report its owner/access/stop instructions, and stop only run-owned resources within cleanup authority; keeping it available does not imply background monitoring.

For incremental Pod updates, use only the authorized development workload and application paths. Record the base image digest plus the copied candidate/patch identity and affected paths; preserve runtime configuration and credentials. Verify that the running process loaded the update after the repository-required compile/reload/restart, then rerun the slice check. Successful copying alone is not activation. Handle removed files explicitly within the owned paths so stale code cannot survive unnoticed. A recreated Pod loses ad-hoc copies: reapply the recorded patch or use a freshly built image before reusing evidence. Label results as development-Pod evidence; they do not establish acceptance of an untested release image. Keep the repository's required final build/deployment checks.

Update current instructions, scope and unresolved prerequisites in the existing Issue description; append identified attempts, first failures, retests, human feedback and cleanup in comments. Prefer links to maintained scripts and existing guides over copying their contents. Keep reusable cases, fixtures and tools in the repository and raw receipts in controlled attachments/storage. Preserve prior notes and evidence; keep credentials out of every record. An explicit document/export request may use the specified carrier, linked to the same Issue, without a second current result table.

Report the Issue entry, write/readback status, verified and unverified routes, missing inputs, and next usable test command. Do not install global clients, restore the retired orchestrator, modify shared environments, or claim full integration acceptance merely because setup is healthy.
